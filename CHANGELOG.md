## [6.3.0] - Unreleased
### Added
- Per-dataset sample weights in `ikpls.fast_cross_validation.jax.PLS.stateless_cross_validate`: `sample_weight` may now be traced by `jax.jit` or `jax.vmap`, e.g. one weight vector per dataset when vmapping over datasets, as in distance-weighted local PLS, where each unknown sample's neighbours are weighted by their distance to it. Previously, traced weights raised a `ValueError`, and only one concrete weight vector, closed over and shared by all datasets, worked, and only under a plain `jax.vmap`. Traced weights cannot be checked inside the traced computation, so check them beforehand, e.g. with `validate_folds` below: they must be non-negative, and each fold's training set needs a non-zero weight when centering or scaling, and more than `ddof` of them when scaling. Invalid traced weights silently give wrong or NaN results. Per-dataset weights cost about the same as no weights: on a GPU, `jax.jit(jax.vmap(stateless_cross_validate))` over 256 datasets of 500 samples and 420 features, with 10 folds and A = 30, takes 344 ms with weights and 341 ms without, and the same memory apart from the weights themselves.
- `ikpls.fast_cross_validation.jax.PLS.validate_folds(validation_indices, N, sample_weight=None)`: checks the concrete validation indices and sample weights of one dataset or a stack of datasets on the host, before `stateless_cross_validate` traces them. It runs the checks that `stateless_cross_validate` runs on concrete inputs (indices in range and distinct within each fold, the training-set size for `ddof`, non-negative weights after the cast to `dtype`, and enough non-zero training weights in every fold), vectorized over the datasets, and names the first failing dataset and fold. For 2,000 datasets of 500 samples with 10 folds, it takes about 4 µs per dataset, against about 60 µs per dataset for a loop over cvmatrix's single-dataset `CVMatrix.validate_folds`.
- New example `examples/local_pls_jax.py`: local PLS for 100,000 samples at once with `jax.vmap`, with the settings of our local PLS benchmark and on its synthetic NIR-like spectra. Each spectrum of a pool of 100,000 is predicted by its own model on its 200 nearest other spectra, found with FAISS if it is installed, else with scikit-learn's `NearestNeighbors`. Each model's number of components (1 to 30) is chosen by 5-fold cross-validation with Venetian blinds over y, with `stateless_cross_validate` under `jax.jit(jax.vmap(...))` and the folds of all models checked by `validate_folds`. The models are then grouped by their number of components, and each group is refitted on its neighbourhoods and predicts its spectra with `ikpls.jax.PLS.stateless_fit`/`stateless_predict` under `jax.vmap`, fitting only the components it needs. X and y are centred, not scaled; K = 2,800 wavelengths with Algorithm #1, or K = 100 with Algorithm #2. With `DISTANCE_WEIGHTED = True`, each model weights its neighbours by their distance to its spectrum, with its own weight vector. On an NVIDIA RTX 3090 Ti, all 100,000 local models take 7.4 s at K = 100 and 3.4 min at K = 2,800, after 15 to 17 s of compilation.
- New example `examples/local_pls_numpy.py`: the same local PLS with NumPy only, for users without JAX. Each model's number of components is chosen with `ikpls.fast_cross_validation.numpy.PLS.cross_validate`, and each model is refitted with that many components and predicts with `ikpls.numpy.PLS`, in chunks spread over the CPU cores with joblib. It gives the same results as `examples/local_pls_jax.py`: the same number of components for all 100,000 models in both settings, and predictions within 1e-12. All 100,000 local models take 42 s at K = 100 and 12 min at K = 2,800 on a 16-core CPU.

### Changed
- Weighted `stateless_cross_validate` calls are now `jax.jit`-compiled internally, as unweighted ones already were, instead of running un-jitted. Repeated eager weighted calls therefore run at compiled speed; as for unweighted calls, the first call with new shapes or settings compiles. For example, with N = 500, K = 420, A = 30, 10 folds and Algorithm #2, a repeated weighted call takes 7.8 ms instead of 107 ms on a CPU and 3.0 ms instead of 147 ms on a GPU, and the first call 0.24 s instead of 1.5 s on a CPU and 2.6 s instead of 6.9 s on a GPU. They also use less memory: in this example, the peak GPU memory use while running falls from 61 MB to 36 MB, the same as for unweighted calls, and the CPU's from about 120 MB to 11 MB; with Algorithm #1 and K = 4,200, the GPU's falls from 599 MB to 302 MB. As for unweighted calls, `metric_function` is now traced once, so what it reads then (values it closes over, globals or its own attributes) is fixed for later calls with the same function; previously, weighted calls ran it anew on every call.
- Concrete `sample_weight` closed over inside the caller's `jax.jit` now works in `stateless_cross_validate`, and is checked on the host as in eager calls, together with the folds if `validation_indices` is concrete too. Previously, it raised a `ValueError`.
- `stateless_cross_validate` requires `sample_weight` of shape (N,) or (N, 1), also when traced. Previously, any shape with N elements, e.g. (1, N), passed its own check; cvmatrix 3.4.0 rejects such weights in any case.
- The errors of `stateless_cross_validate` for out-of-range or duplicate validation indices now name the failing fold, e.g. `Fold 2: ...`, as its errors for weighted folds without enough non-zero training weights already did.
- ikpls now requires `cvmatrix>=3.4.0` (was `>=3.3.0`), in both the base dependencies and the `jax` extra: cvmatrix 3.4.0 accepts traced sample weights, which weighted `stateless_cross_validate` calls now always pass to it, also when called eagerly. Requiring it in the base dependencies too means upgrading ikpls without the extra cannot keep an older cvmatrix next to an installed JAX.
- `ikpls.fast_cross_validation.jax.PLS.cross_validate` now compiles its per-fold computation once per combination of input shapes, settings and `A`, and reuses it in later calls with the same `metric_function`, also with new data and from other instances, as `stateless_cross_validate` already did. Previously, every call traced and compiled it anew, which dominated the time of a call for small and medium-sized problems. Repeated calls are therefore much faster: with N = 2,000, K = 200, M = 10, A = 20 and 20 folds with Algorithm #2, a call takes 15 ms instead of 162 ms on a CPU and 7.8 ms instead of 337 ms on a GPU. A call that compiles, the first one or one with a new `metric_function`, takes about as long as before (in this example, the first call in a new process 0.32 s on a CPU and 4.4 s on a GPU, as before, and a call with a new `metric_function` 164 ms instead of 163 ms on a CPU and 323 ms instead of 337 ms on a GPU), and the peak GPU memory use is the same or lower. The most recently used `metric_function` stays alive between calls, with what it closes over; previously, `cross_validate` kept none. As for `stateless_cross_validate`, `metric_function` is now traced once per such combination, so what it reads then (values it closes over, globals or its own attributes) is fixed for later calls with the same combination.
- `ikpls.jax.PLS.cross_validate` now compiles its per-fold computation once per combination of input shapes, settings, `A` and batch shape, and reuses it in later calls with the same `metric_function` and `preprocessing_function`, also with new data and from other instances with the same settings, as `ikpls.fast_cross_validation.jax.PLS.cross_validate` does. Previously, every call compiled it anew, so a loop of calls, e.g. one per local model, spent nearly all its time compiling: with N = 200, K = 100, A = 30, 5 folds and Algorithm #2, a call takes 1.5 ms instead of 228 ms on a CPU and 1.5 ms instead of 295 ms on a GPU. A call that compiles, the first one or one with new functions, takes about as long as before (in this example, the first call in a new process 0.32 s instead of 0.33 s on a CPU and 1.9 s on a GPU, as before, and a call with a new `metric_function` 229 ms on a CPU, as before, and 288 ms instead of 297 ms on a GPU), and the peak GPU memory use is the same. The two functions are now traced once per such combination, shared by all instances with the same settings, so what they read then (values they close over, globals or their own attributes) is fixed for later calls with the same functions, also from another instance; previously, each new instance traced them anew. The compiled program is built from a new instance constructed from the instance's constructor arguments, so other instance state, e.g. an attribute changed after construction that is not a constructor argument, is not used by `cross_validate`, as for the fast cross-validation. `metric_function` and `preprocessing_function` no longer need to be hashable; previously, unhashable ones, e.g. an instance of a non-frozen dataclass, raised a `ValueError`. A subclass that overrides `stateless_fit_predict_eval` still has it called for every fold, with the functions as its static arguments as before, so there they must still be hashable and stay alive in JAX's caches.
- The internal compilation caches of `ikpls.fast_cross_validation.jax.PLS.stateless_cross_validate` and `cross_validate`, and of `ikpls.jax.PLS.cross_validate`, each keep, per class and constructor settings, only the program compiled for the most recently used `metric_function` (for `ikpls.jax.PLS.cross_validate`, and `preprocessing_function`), separately for weighted and unweighted calls, for the 64 most recently used settings. `metric_function` is matched by identity (the same method of the same object counts as the same), so another object -- a function created per call, or a new instance of a callable class, even an equal one -- compiles anew and replaces the program, as does alternating between two functions. Define one function and reuse it, and return several metrics from it if needed. Cycling through more than 64 settings compiles on every call. Settings are matched by value and type (also inside tuples), so equal values of different types that can compute differently, e.g. `ddof=1` and `ddof=np.float64(1.0)`, do not share a program. A `metric_function` that is not hashable, e.g. an instance of a non-frozen dataclass, is now compiled and reused too, so changes to what it reads, e.g. its attributes, no longer take effect for the same object; previously, `stateless_cross_validate` ran such calls un-jitted. Previously, the cache of `stateless_cross_validate` kept the 64 most recently used combinations of settings and `metric_function`, matched by hash and equality, so equal hashable metric objects created per call, e.g. frozen dataclasses, reused it.
- Predictions with centering or scaling are computed as `X @ B' + b0`, with the centering and scaling of X and Y applied to the regression coefficients (`B' = B / X_std.T * Y_std` and `b0 = Y_mean - X_mean @ B'`) instead of to X, when that is faster: when X has at least 8 times as many numbers as B, i.e. for at least 8·M samples with one number of components and 8·A·M with all of them. By operation count, folding pays off from about twice as many; the margin covers the dispatch of the extra small operations, which depends on the hardware. X is then read only by the matrix product. This applies to `ikpls.numpy.PLS.predict`, `ikpls.jax.PLS.predict` and `stateless_predict`, and so `ikpls.sklearn.PLS.predict`, and to the validation predictions of `ikpls.numpy.PLS.cross_validate`, of `ikpls.jax.PLS.cross_validate` and `stateless_fit_predict_eval`, and of both fast cross-validations, for inputs of the documented shapes: X of shape (N, K) with means and standard deviations of shape (1, K) and (1, M). Other inputs, and shapes that are symbolic, e.g. a variable number of samples in `jax.export`, are predicted from centred X as before. For example, for 10,000 samples with K = 500, M = 5 and 20 of 30 components, centred and scaled, `ikpls.numpy.PLS.predict` takes 0.49 ms instead of 12 ms, and `ikpls.jax.PLS.predict` 0.36 ms instead of 8.6 ms on a CPU and 0.22 ms instead of 0.30 ms on a GPU. `ikpls.numpy.PLS.predict` then also does not copy X (here 40 MB). The predictions change only by rounding, but that rounding error grows with how far the columns of X lie from zero relative to their spread, as `X @ B'` and `X_mean @ B'` then nearly cancel: in our measurements, the largest error relative to the spread of the predictions was 3e-15 with centering first, and 4e-15, 2e-13 and 3e-11 with `X @ B' + b0` at a ratio |mean| / std of the columns of 1, 100 and 10,000 in float64; in float32, 1e-6 with centering first and 2e-6, 9e-5 and 1e-2.
- `ikpls.fast_cross_validation.numpy.PLS.cross_validate` prints its "Cross-validating ..." summary line only if `verbose` is non-zero. Previously, it printed the line even with `verbose=0`.

### Fixed
- `ikpls.jax.PLS.cross_validate` no longer keeps the metric and preprocessing functions of earlier calls alive. Every function it was called with stayed in JAX's internal caches, as a static argument of the internally jitted functions, together with everything it closes over, until JAX evicted thousands of entries or `jax.clear_caches()` ran. For example, after 20 calls, each with a new metric function that closes over an 8 MB array, 160 MB stayed allocated, on a CPU and on a GPU alike; now only the most recently used function stays, with the 8 MB it closes over, as for the fast cross-validation.
- `ikpls.jax.PLS.predict` predicted with the instance's first fit after the instance was fitted again, e.g. in a loop that refits one instance per dataset: its compiled program had the regression coefficients, means and standard deviations of the fit it was first compiled after built in, per shape of `X` and `n_components`. It now always uses the latest fit. This affected every release since 3.1.0 with JIT enabled, the default. `predict` itself is no longer `jax.jit`-compiled; it passes the fitted matrices to a compiled `stateless_predict`, so it still runs compiled. That is a variant of `stateless_predict` with the product for all components computed as an einsum, which is faster when B is an argument of the program; as before, an override of `stateless_predict` in a subclass is called instead. Passing the fitted matrices costs about 1.4 µs per call on a CPU and about 2 µs on a GPU, which shows only in predictions of a few samples: for one sample with K = 2,800 and 12 of 30 components, `predict` takes about 8.9 µs instead of 7.5 µs on a CPU and 59 µs instead of 56 µs on a GPU, and with all 30 components as long as before. Building them in again would mean compiling anew after every fit.
- `ikpls.fast_cross_validation.jax.PLS.stateless_cross_validate` no longer keeps metric functions alive after they are replaced. A `metric_function` created anew per call, e.g. a lambda or a function defined inside a loop, stayed in the compilation cache with its compiled program and everything it closes over until 64 newer ones had replaced it. For example, after 80 calls, each with a new metric function that closes over an 8 MB array, 512 MB of GPU memory stayed allocated (8 MB for each of the 64 kept functions); now only the most recent function's 8 MB does, and the host memory kept falls from about 1 GB to 0.2 GB, which is memory JAX itself keeps per compilation.
- `ikpls.fast_cross_validation.jax.PLS` no longer keeps an internal fitter per instance alive. Each instance built its own internal `ikpls.jax.PLS` fitter, which JAX's caches kept, together with what was traced for it, as a static argument of its jitted methods; so a loop that creates a new instance per call, e.g. one per local model, kept one fitter per call and compiled on every call. For example, with N = 200, K = 100, A = 30, 5 folds and Algorithm #2, 40 calls of `cross_validate`, each on a new instance, kept 40 fitters, the process grew by about 2.5 MB per call, and a call took 226 ms; now all instances with the same `algorithm` and `dtype` share one fitter, the process does not grow, and a call takes 1.4 ms. Likewise, `stateless_cross_validate` and `ikpls.jax.PLS.cross_validate` reuse the instance their compiled programs are built from, also after its settings were evicted from the compilation cache, for as long as JAX's caches keep it.
- `ikpls.fast_cross_validation.jax.PLS.stateless_cross_validate` compiled the program of a subclass whose constructor forwards the base class's constructor arguments through `**kwargs` from the subclass's own arguments only, so the forwarded settings, e.g. `algorithm` or `scale_X`, silently reverted to their defaults. It now uses all constructor arguments, and runs un-jitted if a new instance constructed from them does not reproduce them.
- `ikpls.fast_cross_validation.jax.PLS` now carries each fold's last numerically stable component forward, as `ikpls.jax.PLS` and the NumPy fast cross-validation already did: when more components are requested than a fold's training `X` supports, e.g. beyond its numerical rank, the predictions with the excess components equal those with the last stable component. Previously, the excess components were built from round-off noise, and their validation MSEs could reach about 1e35. This rarely changed the number of components that minimizes the validation error, but it could when the folds' ranks differ, as one fold's excess components then dominated the average over folds. Both fast cross-validation entry points, `cross_validate` and `stateless_cross_validate`, now use the same stability criteria as the NumPy fast cross-validation. With Algorithm #2, the first component past a fold's numerical rank often lies close to the stability threshold, so either implementation may admit one round-off component there, and their results for more components may then differ. The stability check adds a few operations to compile, so a first call can take up to about 4% (about 10 ms) longer; later calls reuse the compiled program and run as fast as before.
- Gradients with respect to the sample weights are no longer NaN where a weight is exactly zero with Algorithm #1, in both `ikpls.jax.PLS(algorithm=1)` and `ikpls.fast_cross_validation.jax.PLS(algorithm=1)`. Algorithm #1 scaled the rows of `X` by the square roots of the weights, and the square root's infinite derivative at zero turned these gradients into NaN, even though the regression coefficients and predictions have finite derivatives there. It now applies the weights to the scores instead, so the gradients are finite and equal Algorithm #2's. `B`, the predictions and `max_stable_components` are unchanged up to floating-point round-off. So are `W`, `P`, `Q`, `R` and `T`, except for components past `max_stable_components`, which are numerical noise in any case, and for the arbitrary sign of a component, which round-off can flip when M ≥ K. `T` still holds the weighted scores `sqrt(W) X R`; as the square root is not differentiable at zero, the derivative of a zero-weight sample's weighted scores with respect to its own weight is taken as zero.

## [6.2.0] - 2026-10-31
### Added
- Support for Python 3.15: `requires-python` is now `>=3.10, <3.16`, the package declares the Python 3.15 classifier, and Python 3.15 was added to the CI test matrices (with and without JAX, on Linux, Windows and macOS).
- Free-threaded Python 3.15t in the CI test matrices, on Linux, Windows and macOS, and the `Programming Language :: Python :: Free Threading :: 2 - Beta` classifier. The JAX job skips Windows, where jaxlib publishes no free-threaded build; the NumPy-only job covers it. A free-threaded interpreter re-enables the GIL, with only a `RuntimeWarning`, when it imports an extension module without free-threading support. So a CI step fails the job if importing the test dependencies re-enables it, and `tests/conftest.py` fails the test run if any module imported during the tests does.
- `ikpls.fast_cross_validation.jax.PLS.stateless_cross_validate(X, Y, A, validation_indices, metric_function, sample_weight=None)`: a purely functional, `jax.jit`/`jax.vmap`-able variant of `cross_validate` -- the fast cross-validation analogue of `ikpls.jax.PLS.stateless_fit`. It takes the validation indices of equally sized folds as a 2-D integer array of shape `(n_folds, N_val)` (fixed shapes are what make it `vmap`-able), stores nothing on the instance, and returns the `metric_function` pytree stacked over the folds along a new leading axis instead of a dict. `jax.vmap` it over a leading dataset axis of `X` `(B, N, K)`, `Y` `(B, N, M)` and `validation_indices` `(B, n_folds, N_val)` -- and wrap in `jax.jit` -- to cross-validate many independent datasets (e.g. one local PLS model per sample, per pixel, or per experimental condition) in a single compiled program; a Python loop over `cross_validate` would instead recompile and pay a host round-trip per dataset.
  - Unweighted calls with a hashable `metric_function` are `jax.jit`-compiled internally, so eager calls run at compiled speed; nesting inside a caller's `jax.jit`/`jax.vmap` is fine. The compiled program is built from the instance's constructor arguments, read from the attributes of the same names (the scikit-learn convention, which subclasses must follow), and cached per class, constructor arguments, input shapes, `A` and `metric_function` rather than per instance: instances stay picklable and copyable, and changing an instance's settings takes effect. Only the 64 most recently used combinations of class, constructor arguments and `metric_function` are kept compiled, so a `metric_function` created anew per call (which recompiles: define it once) is not retained indefinitely; values a `metric_function` closes over are captured when it is first compiled. Weighted calls, and calls with an unhashable `metric_function` or constructor argument, run un-jitted.
  - Per-fold results agree with `cross_validate` up to floating-point round-off (both are built on the same per-fold function; XLA may fuse operations differently across jit boundaries).
  - Invalid inputs are rejected host-side: `X` and `Y` with different numbers of rows; non-rectangular, non-2-D or non-integer indices; `N_val == 0` or `N_val >= N`; out-of-range or duplicate indices when the indices are concrete (NumPy or concrete JAX arrays, also when closed over inside the caller's `jax.jit`, but not when they are a traced argument of the caller's `jax.jit` or `jax.vmap`); a 64-bit `dtype` with `jax_enable_x64` off; negative or wrongly sized weights; and folds too small for the requested scaling (a shape-only check that also runs under tracing).
  - `sample_weight` is supported eagerly and under a plain `jax.vmap` with one concrete, closed-over weight vector; under `jax.jit` (or as a traced argument) it raises a `ValueError` with an explicit message, because the cvmatrix backend validates weights host-side.

### Changed
- Fast cross-validation with Improved Kernel PLS Algorithm #1 (`ikpls.fast_cross_validation.numpy.PLS` and `ikpls.fast_cross_validation.jax.PLS`) no longer forms the dataset-wide `X^T W X`. Algorithm #1 downdates only `X^T W Y` and the centering/scaling statistics, but `cvmatrix.CVMatrix.fit` always formed the `(K, K)` product as well; for wide `X`, the case Algorithm #1 is meant for, that unused product could dominate the run time, and it cost `K * K` memory. For example, with `N = 500`, `K = 4200`, `M = 1`, `A = 30` and 10 folds on one BLAS thread, the product alone took 0.16-0.18 s of the NumPy fast cross-validation's 0.33-0.39 s per call, about half. Both backends now construct their `CVMatrix` with `compute_XTX=False` for Algorithm #1, which skips the product and leaves `XTX` as `None`. Results are unchanged; Algorithm #2, which needs `X^T W X`, is unaffected. In the JAX backend the saving applies to `cross_validate` and to the un-jitted `stateless_cross_validate` calls (weighted, or with an unhashable `metric_function` or constructor argument); under `jax.jit`, the unused product is dropped from the compiled program anyway.
- The minimum required `cvmatrix` version is now `>=3.3.0` (was `>=3.2.2`), in both the base dependencies and the `jax` extra: `compute_XTX`, used above, was introduced in cvmatrix 3.3.0.
- `ikpls.numpy.PLS.cross_validate` no longer fits the instance itself (see the thread-safety fix below). Previously, when the folds ran in the calling process (`n_jobs=1`, a single fold, or joblib's threading backend), the instance was left fitted on the last fold to be fitted, a `metric_function` could read the current fold's model from the instance, and a `preprocessing_function` the previous fold's; with `n_jobs > 1` on the default process-based backend this never happened. Code that called `predict` on the instance after `cross_validate` must now call `fit` first (`predict` otherwise raises `NotFittedError`). One fold model of the last call is kept outside the instance (released with it, and neither pickled nor copied with it), so repeated calls run as fast as before and hold the same memory as the fitted instance did.
- CI: all GitHub Actions were updated to their latest releases (`actions/checkout@v7`, `actions/upload-artifact@v7`, `actions/download-artifact@v8`, `astral-sh/setup-uv@v10.3.3`, `sigstore/gh-action-sigstore-python@v3.5.0`), and the package is built with Python 3.15. setup-uv no longer publishes moving major tags, so it is pinned to an exact release. The test jobs now install with `uv sync --locked`, so an outdated `uv.lock` fails the job instead of being silently re-locked, and the release job reads the version from `pyproject.toml` with `tomllib` instead of an unanchored `grep` that could also match other `version = "..."` keys.

### Fixed
- `ikpls.numpy.PLS.cross_validate` is now thread-safe. Each fold called `fit` and then `predict` on the shared instance, so when folds ran concurrently in one process (joblib's threading backend, e.g. via `joblib.parallel_config(backend="threading")`), one fold could overwrite another's model between its `fit` and `predict`; in our tests most folds' metrics were then wrong, by tens to hundreds of percent. The folds are now fitted on shallow copies of the instance, one per thread, so concurrent folds never share a model; run time and memory are unchanged. The default process-based (loky) backend was not affected, since each worker process gets its own copy, and neither the fast cross-validation classes nor the JAX `cross_validate` had this bug.
- `ikpls.fast_cross_validation.jax.PLS` now uses its current `algorithm` and `dtype` when they are changed after construction. It kept the fitter chosen at construction, so `cross_validate` combined the new algorithm's training matrices with the old algorithm's fit.
- `ikpls.fast_cross_validation.jax.PLS.cross_validate` no longer reads the sample count back from the instance while it runs, so concurrent calls on one instance with datasets of different sizes can no longer pick up each other's `N` (the instance's `N`, `K`, `M` and `A` attributes still describe the most recent call).
- `copy.deepcopy` and `pickle` of a fast cross-validation `PLS` (NumPy or JAX) holding a fitted `cvm` work again: they failed since cvmatrix 3.2.0, whose `CVMatrix` stored a module object; cvmatrix 3.3.0, now required, fixed it.
- The publish workflow now builds, publishes and tags the commit whose Tests run passed (`github.event.workflow_run.head_sha`). Previously it checked out the newest commit on `main`, so a commit pushed while the Tests run was in progress could be published untested. Only a successful Tests run for a push to this repository's `main` publishes, its build job is skipped otherwise, and the build action no longer checks out the repository a second time, which would have reset the commit to the default ref.

## [6.1.2] - 2026-07-16
### Changed
- Micro-optimized the improved Y-loadings `Q` in the `2 <= M < K` branch of the shared inner loop (`ikpls._impl.pls_steps`; NumPy backend and its fast cross-validation). `q = q_eig * sqrt(eig_vals[-1]) / tTt` is now `q = q_eig * (sqrt(eig_vals[-1]) / tTt_val)`, collapsing two array ufuncs into one by reusing the Python float `tTt_val` already computed for the stability guard. At small `M`, where the step is dispatch-bound, this makes `Q` ~25% faster in-fit and removes a small regression where the element-wise `Q` was slower than the original matmul form (larger `K`/`M` were already faster). Not bit-identical (a ~1-ULP reassociation); `predict`/`cross_validate` unchanged to floating-point tolerance and the array dtype is preserved (NEP 50). JAX backend unchanged (XLA already fuses the expression).

## [6.1.1] - 2026-07-13
### Changed
- Micro-optimized the computation of the PLS X-rotations `R` (step 3 of the shared Improved Kernel PLS inner loop in `ikpls._impl.pls_steps`, used by `ikpls.numpy.PLS` and `ikpls.fast_cross_validation.numpy.PLS`). The direct matrix form `r_a = w_a - R_{a-1} (P_{a-1}^T w_a)` is now used only from the third component onward; the first two components are special-cased to their algebraically identical base cases — `r_1 = w_1` (a plain copy) and `r_2 = w_2 - (p_1^T w_2) r_1` (a single vectorized rank-1 update, `w - PT[:1] @ w * RT[:1].T`). The general matrix form incurred avoidable overhead at low component counts: at `a = 1` it evaluated matrix products over empty `(0, K)` slices, and at `a = 2` it expressed the single rank-1 update as a `(K, 1) @ (1, 1)` BLAS matmul whose per-call overhead exceeds a plain broadcast multiply. With the special cases, the improved `R` is now at least as fast as the original sequential recurrence at every `(A, K)` measured; previously the matrix form was slower for `A <= 2` (up to ~2x slower at `K = 10000`) before overtaking the recurrence from `A >= 3`. The output is bit-for-bit identical to the previous release (the rotations are mathematically unchanged; only the arithmetic grouping for the first two components differs), so all fitted matrices and `predict` / `cross_validate` results are numerically unchanged. Performance-only; no API or behavior change. The JAX backends are unaffected: they already compute `R` as a fixed-shape masked matmul inside a `jax.lax.scan`, where the per-component Python/dispatch overhead this addresses does not exist.

## [6.1.0] - 2026-07-08
### Changed
- `ikpls.sklearn.PLS` now validates its constructor parameters through scikit-learn's `_parameter_constraints` / `_validate_params` at fit time, replacing the previous ad-hoc `_validate_n_components` check. `n_components` is constrained to `Interval(Integral, 1, None)`, `algorithm` to `Options({1, 2})`, the centering/scaling flags to booleans, and `ddof` to a non-negative integer; invalid values now raise scikit-learn's standard `InvalidParameterError` (a `ValueError`) with a uniform message, and `algorithm` is validated up front rather than by the inner NumPy `PLS`. As with scikit-learn's own `PLSRegression`, `n_components=True` is accepted (a `bool` is an `Integral` equal to 1). The public method signatures also gained type hints; the constructor parameters are intentionally left unannotated so the sklearn "store verbatim, validate at fit" contract (and the `typeguard`-instrumented test suite) is preserved, and the package still ships no `py.typed`, so external static type checkers are unaffected. The array-like data arguments of the public methods (`X` / `y` / `sample_weight`) are typed `Any` rather than `numpy.typing.ArrayLike`: each method is a validation boundary that defers to scikit-learn's `validate_data` / `check_array`, and a strict annotation would make `typeguard` raise on the sparse input that `check_estimator` deliberately passes, pre-empting the wrapper's own conformant rejection (this previously failed `check_estimator`'s sparse-tag check on the Python versions that resolve a scikit-learn/scipy where it is strict).
- `ikpls.sklearn.PLS.fit_transform` now returns the `(X-scores, Y-scores)` tuple, matching `sklearn.cross_decomposition.PLSRegression.fit_transform` and `ikpls.numpy.PLS.fit_transform`. Previously the wrapper inherited `sklearn.base.TransformerMixin.fit_transform`, which calls `transform(X)` and therefore returned only the X-scores (ignoring `Y`). The override fits through `fit` (so a subclass overriding `fit` still runs) and returns `transform(X, y)`, keeping `fit_transform` consistent with `fit(...).transform(...)`. This is a behavior change for callers that relied on the previous X-scores-only return.
- As a consequence, `ikpls.sklearn.PLS` now has two expected failures in scikit-learn's `check_estimator` suite (`check_transformer_general` and `check_transformer_data_not_an_array`). Those checks compare `fit_transform(X, y)` against `transform(X)`; scikit-learn only compares the `(X-scores, Y-scores)` tuple against the tuple-returning `transform(X, y)` for a hard-coded set of class names (`CROSS_DECOMPOSITION`: `PLSRegression`, `PLSCanonical`, `CCA`, `PLSSVD`), and this class is named `PLS`. scikit-learn's own `PLSRegression` has identical tuple behavior and passes only by virtue of its name, so these are not real conformance defects; the conformance test marks them as expected failures.
- `max_stable_components` (on `ikpls.numpy.PLS` and both JAX classes) is now determined from the X-**score** norm in addition to the X-weight norm. Previously it was reduced only when an X-weight norm underflowed below machine epsilon; that detects an exhausted X-Y cross-covariance (e.g. a constant target) but misses ordinary numerical-rank deficiency (wide `p > n` data, collinear features), where the weight norm stays finite while the component lies in the null space of the (centered) `X`. Such a component now trips a *relative* score-norm test — `‖t_a‖² ≤ eps · max(‖t_j‖²)` over the components seen so far — so `max_stable_components` reflects the numerical rank. The NumPy and JAX backends use the same running (cumulative) max, so they agree even when the per-component score norms are non-monotonic (e.g. unscaled data where a high-covariance/low-variance component is extracted before a high-variance one). The relative threshold leaves legitimately small-magnitude data fully stable.
- Regression coefficients for components beyond `max_stable_components` are now carried forward. A null-space component adds no predictive information, so `predict`/`cross_validate` with more than `max_stable_components` components now return exactly the same result as with `max_stable_components` components, rather than the numerically meaningless output that over-extraction past the numerical rank previously produced.
- The fit-time underflow `UserWarning` (NumPy backend) was generalized: it now reports either an X-weight underflow (`"X weight is close to zero."`) or an X-score-norm collapse (`"X score norm is close to zero ..."`) and states that predictions with more components are identical to predictions with `max_stable_components` components (replacing the previous "may be unstable" wording). Internal: the duplicated per-class `_weight_warning` methods were replaced by a single shared `_stability_warning` in `ikpls._impl.pls_steps`.
- `ikpls.sklearn.PLS` now exposes `max_stable_components_` as a fitted attribute (from the inner NumPy model's `max_stable_components`).

## [6.0.0] - 2026-07-01
### Added
- `ikpls.sklearn.PLS`: a thin, fully scikit-learn-conformant wrapper around the NumPy `ikpls.numpy.PLS`, mirroring `sklearn.cross_decomposition.PLSRegression`. It is both a regressor (`predict` / `score(X, y, sample_weight=None)`) and a dimensionality-reducing transformer (`transform` / `inverse_transform`, each supporting both `X` and `Y`), and passes scikit-learn's `check_estimator` suite with no expected failures. `n_components` is a constructor parameter, so the wrapper drops directly into `cross_validate`, `Pipeline`, and `GridSearchCV`. It exposes the `PLSRegression` fitted attributes `x_weights_`, `y_weights_`, `x_loadings_`, `y_loadings_`, `x_rotations_`, `y_rotations_`, `coef_`, `intercept_`, and `n_features_in_`. Following `PLSRegression` (whose `y_weights_` equals its `y_loadings_`), `y_weights_` equals `y_loadings_`. `coef_` and `intercept_` match `PLSRegression` value-for-value: `intercept_` is the (weighted) `Y`-mean and, as in scikit-learn, `predict` effectively centers `X` (so `predict(X) == (X - X_mean) @ coef_.T + intercept_`). `y_rotations_` is computed lazily on first access (it requires a pseudo-inverse) and cached, so `fit` never pays for it unless it is used. The fast all-components prediction (shape `(A, N, M)`) is preserved via `predict_all_components`, bit-identical to the inner `PLS`. The wrapper performs input validation and plumbing only; all PLS math is delegated unchanged to the inner `PLS`, so the native fast paths (`PLS.fit(X, Y, A)`, `PLS.cross_validate`, and the JAX implementations) are untouched.
- `C` (PLS Y-weights) attribute on the NumPy `ikpls.numpy.PLS` and the JAX `ikpls.jax.PLS` classes (shape `(M, A)`). In Improved Kernel PLS the Y-weights equal the Y-loadings `Q` (this is scikit-learn's `PLSRegression` convention, where `y_weights_` equals `y_loadings_`), so `C` is exposed as a zero-cost alias of `Q`: it adds no computation to `fit` / `stateless_fit` and is never referenced inside a jitted region, so `jax.vmap` and all fast paths are unaffected. Not added to the fast cross-validation classes, which expose no loading/weight matrices.

### Changed
- **Breaking:** Modules were reorganized into a consistent backend-named layout. The NumPy PLS moved from `ikpls.numpy_ikpls` to `ikpls.numpy`; the JAX PLS is now a single `ikpls.jax.PLS(algorithm=1|2)` class (the former `ikpls.jax_ikpls_alg_1`, `ikpls.jax_ikpls_alg_2`, and `ikpls.jax_ikpls_base` modules are now private under `ikpls._impl`); the fast cross-validation modules are now `ikpls.fast_cross_validation.numpy` and `ikpls.fast_cross_validation.jax` (renamed from `numpy_ikpls` / `jax_ikpls`); and the (new) scikit-learn wrapper class is named `PLS` in `ikpls.sklearn`, consistent with the other backends. Update imports to, e.g., `from ikpls.numpy import PLS`, `from ikpls.jax import PLS`, `from ikpls.sklearn import PLS`, `from ikpls.fast_cross_validation.numpy import PLS`, and `from ikpls.fast_cross_validation.jax import PLS`. `ikpls.jax.PLS(algorithm=...)` returns the selected algorithm's implementation while remaining `isinstance` / `issubclass`-compatible with `ikpls.jax.PLS` and exposing `.algorithm`.
- **Breaking:** The default `ddof` for the (weighted) standard deviation used in scaling is now `0` (was `1`) across all PLS classes (`ikpls.numpy`, the JAX classes, and both fast cross-validation classes) and the `ikpls.sklearn.PLS` wrapper. `ddof=0` matches scikit-learn's frequency-weight `sample_weight` semantics, so `ikpls.sklearn.PLS` passes scikit-learn's `sample_weight`-equivalence check with no expected-fail. Note that scikit-learn's own `PLSRegression` scales with `ddof=1`; pass `ddof=1` explicitly to reproduce its scaling. Weighted or scaled fits that relied on the previous `ddof=1` default change numerically; pass `ddof=1` to retain the old behavior.
- **Breaking:** The per-sample weights parameter was renamed from `weights` to `sample_weight` across the entire public API -- `fit`, `fit_transform`, and `cross_validate` on the NumPy (`ikpls.numpy`) and JAX (`ikpls.jax`) PLS classes (plus `stateless_fit` on the JAX classes, which have no NumPy counterpart), and `cross_validate` on both fast cross-validation classes (`ikpls.fast_cross_validation.numpy` / `.jax`) -- to match scikit-learn's `sample_weight` naming convention (already used by the `ikpls.sklearn.PLS` wrapper). Callers that passed `weights=` by keyword must switch to `sample_weight=`; positional calls are unaffected.
- The minimum required `scikit-learn` version is now `>=1.6.0` (was `>=1.5.0`); the conformant wrapper relies on `sklearn.utils.validation.validate_data` and the `__sklearn_tags__` API introduced in 1.6.
- `tqdm` moved from the base dependencies to the `jax` extra, since it is only used by the JAX implementations (the `cross_validate` progress bars). A NumPy-only `pip install ikpls` no longer installs `tqdm`; it is still installed by `pip install ikpls[jax]`.
- The minimum required `cvmatrix` version is now `>=3.2.1` in both the base dependencies (was `>=3.0.0`) and the `jax` extra (was `>=3.2.0`): cvmatrix 3.2.1 no longer imports JAX at import time, which the lazy JAX-optional import layout relies on.

### Removed
- **Breaking:** `ikpls.numpy.PLS` no longer subclasses scikit-learn's `BaseEstimator`. Its native API (`fit(X, Y, A)` with the component count as a fit argument, and `predict` returning all component counts at once) is not scikit-learn-conformant and the `BaseEstimator` inheritance was non-functional for real scikit-learn integration. For use inside the scikit-learn ecosystem, use the new `ikpls.sklearn.PLS` wrapper instead. Code relying on `isinstance(pls, BaseEstimator)`, `sklearn.base.clone(pls)`, or `pls.get_params()` / `set_params()` on the raw NumPy `PLS` must switch to `ikpls.sklearn.PLS`.

### Fixed
- `ikpls.fast_cross_validation.numpy.PLS` (Algorithm #1): calling `cross_validate` WITHOUT `sample_weight` on an instance previously used for a weighted `cross_validate` no longer silently applies the previous call's square-root weights to each fold's training rows; the stale weights are now reset, so a reused instance gives the same results as a fresh one.
- The JAX PLS implementations now degrade gracefully to finite zeros (zero weights/loadings/rotations) instead of producing `NaN` when a component underflows -- e.g. an entirely-constant `Y` with no X-Y covariance (`max_stable_components == 0`). This matches the NumPy implementation and scikit-learn's `PLSRegression` (whose `x_rotations_` is zero in that case). The `jax.lax.scan` fit cannot break out of the component loop as the NumPy loop does, so the weight-norm and `t^T t` divisions are now guarded; stable components are numerically unchanged. The standardization of a constant (zero-variance) feature is likewise guarded before its square root, so reverse-mode gradients through such a fit are finite (forward-mode already was); the standard-deviation values are unchanged for every input real data can produce -- the pre-sqrt clamp differs from the old post-sqrt clamp only for a variance within one ULP of `eps**2`, which is unreachable in practice. (Gradients through a fully-degenerate, entirely-constant-`Y` fit remain undefined in both forward and reverse mode -- the underlying norm/eigendecomposition derivatives at exactly zero / repeated eigenvalues are -- but merely over-extracting components on ordinary data does not trigger this.)

## [5.0.0] - 2026-06-30
### Removed
- **Breaking:** The `differentiable` constructor parameter of the JAX PLS classes (`jax_ikpls_alg_1.PLS`, `jax_ikpls_alg_2.PLS`, and `jax_ikpls_base.PLSBase`) has been removed. The `jax.lax.scan` fit and the fixed-size masked-matmul deflation make the JAX implementations end-to-end reverse-mode differentiable by construction, so the separate non-differentiable code path no longer exists and the flag is obsolete. Code that passed `differentiable=...` must drop the argument.
- **Breaking:** The JAX PLS implementations no longer emit the "weight is close to zero" underflow warning. That warning relied on an ordered host `io_callback` that is incompatible with `jax.vmap` and runs counter to JAX's fast, batched execution model; the JAX fit now runs warning-free and is therefore directly `jax.vmap`-able (e.g. to batch many fits). `max_stable_components` is still tracked: it is now computed on-device (no host callback), so it is reported for a single `fit` and is additionally returned by `stateless_fit` (so it is available per fit under `jax.vmap`). The NumPy implementations are unchanged.

### Added
- JAX fast cross-validation: `ikpls.fast_cross_validation.jax_ikpls.PLS`, a GPU/TPU-friendly counterpart to the NumPy fast cross-validation. It computes per-fold training matrices by rank-update via the `cvmatrix` JAX backend and batches the folds with `jax.vmap`. Supports both Improved Kernel PLS Algorithm #1 and #2 and takes a `batch_size` argument to bound memory. Requires `ikpls[jax]` and `cvmatrix[jax]`.

### Changed
- The JAX fit (`stateless_fit`) now iterates components with `jax.lax.scan` instead of an unrolled Python loop, making the traced graph O(1) in the number of components. Cold (compile-dominated) single fits are dramatically faster at large component counts; warm execution and all numerical results are unchanged.
- The JAX `cross_validate` now batches folds with `jax.vmap` (with a new `batch_size` argument to bound memory) instead of looping over folds in Python, substantially accelerating cross-validation.
- Switched build and development tooling from Poetry to [uv](https://docs.astral.sh/uv/): the project now uses PEP 621 `[project]` metadata, the `hatchling` build backend, and a PEP 735 `[dependency-groups]` dev group (`poetry.lock` is replaced by `uv.lock`). The published package and its runtime dependencies are unchanged, except that the `jax` extra now explicitly requires `cvmatrix>=3.2.0` (the JAX fast cross-validation relies on the cvmatrix JAX backend introduced in that release).
